# Optimizations

## Runtime contention and disk-I/O pass

The July 2026 performance pass targeted work that continued even when it could not improve the visible frame, as well as synchronous disk activity on the UI thread.

- Configuration saves are debounced for 500 ms, serialized once per settled revision, and written by one background worker through a same-directory temporary file. Identical JSON is skipped, in-flight and pending revisions are tracked separately so an `A -> B -> A` edit cannot persist stale `B`, and shutdown drains the last revision. This replaces full, synchronous `%AppData%\lifeviz\config.json` rewrites from slider and text-change events.
- Session logging is nonblocking for callers. A bounded 512-record queue feeds one below-normal writer, batches output, flushes no more than every 500 ms, and caps each launch at 8 MiB. The offline audio decoder resets PCM timestamps, and expected `Parsed_realtime` / `Parsed_arealtime` discontinuity-reset warnings are suppressed before enqueue, preventing both warning classes from flooding the queue or adding disk-write churn.
- File metadata probing is lazy and process-wide. Direct videos also initialize asynchronously in a pending state. Sequence, AutoClip, and direct layers share at most two `ffmpeg` probes, with one 15-second deadline covering both the queue and subprocess. The cache is capped at 256 tasks, local successes include file size/write time in their key, and failures retry after a 10-second backoff. The same cached result carries source FPS, codec, and alpha-tag metadata for pacing and selective transparent-WebM decode; no extra probe is launched. Offline sequence/AutoClip handoffs share one deadline across paths and later frames; an exhausted source is skipped for that export rather than multiplying the timeout by the library size.
- Disabled sources are rejected before capture and before both compositors. Disabled file, sequence, and AutoClip decoders suspend without overwriting explicit pause state; window and webcam sessions are released. A disabled parent group makes every descendant effectively disabled, including media added later or resolved asynchronously. Minimizing the main window or suspending Windows likewise stops live media decoders, and restore/wake resumes from held positions with fresh-frame activation; a fixed-duration offline export remains active while minimized.
- The GPU source compositor retains an LRU cache of D3D11 upload texture/SRV pairs keyed by source dimensions, capped at eight entries and 64 MiB (or one unusually large active entry). Mixed-resolution stacks can alternate dimensions without destroying and recreating the same resources each frame or retaining eight 4K allocations.
- Window capture is paced to approximately 30 fps rather than polling `PrintWindow`/BitBlt nearly continuously. Removal cancels immediately and defers GDI resource disposal until an in-progress capture actually exits, avoiding a UI-thread wait and teardown race.
- Inline `Sim Group` presentation no longer publishes a shared snapshot slot immediately after an asynchronous `CopyResource`/`Flush`. The producer keeps at most one snapshot copy in flight and publishes its slot only after a producer event query reports completion. The WPF presentation device caches each ring handle for the current resource generation, copies a published snapshot into its own private underlay, and holds the producer-slot lease until one of three consumer event queries confirms that read completed. A leased slot cannot be selected for another producer copy. If either side saturates, presentation holds the previous private underlay instead of blocking the UI thread or falling back to the live mutable texture. Query failure/timeout keeps leases owned until the presentation device resets, favoring a held frame over unsafe reuse. This two-sided protocol covers the dedicated inline `Sim Group` snapshot handoff only; it does not synchronize every pre-existing non-inline shared-GPU resource path.
- Normal rendering no longer builds profiler metric names, freshness summaries, or timing stamps unless profiling or **Show FPS** needs them. Source mapping coefficients are reused while dimensions are unchanged.
- **Show FPS** refreshes its text and rolling gap summary at 6 Hz while its graphs keep their independent capped cadences. FFT storage and waveform-history scratch storage are reused instead of allocated on each audio quantum.

## FFmpeg process lifecycle and AutoClip churn

An AutoClip library with hundreds of files does not open hundreds of decoders at once. Each scheduled clip chooses one file and seek offset, then cold-starts one decoder for that command. For a zero-delay live handoff only, LifeViz opens exactly one successor up to one second before the boundary while the outgoing decoder remains visible and moving. An AutoClip therefore owns and tracks at most two video decoders during the seam; boundary promotion immediately requests termination of the outgoing process and cleanup returns ownership to one. A long session can accumulate a large process-start count without a library-wide prewarm or resident pool. Reusing one FFmpeg process across arbitrary inputs is not available here because both the input file and seek position are fixed when FFmpeg starts.

The lifecycle pass keeps the required clip handoffs while removing avoidable work:

- Every LifeViz-owned FFmpeg-family child—video/audio decode, metadata probe, recorder encoder, and mux job—starts through one manager. The manager tracks the child and, on Windows, assigns it to a Job Object configured with `KILL_ON_JOB_CLOSE`. Normal teardown first kills the whole process tree with a bounded wait; closing the Job handle is the crash/forced-exit backstop. This prevents a decoder from surviving LifeViz and consuming CPU after the app is gone.
- When `ffmpeg.exe` on `PATH` is a Chocolatey shim, the manager safely resolves and launches the package's real `ffmpeg.exe` under Chocolatey's `lib` directory. This avoids paying for a short-lived shim process on every probe, clip handoff, recording, or mux operation while preserving ordinary `PATH` behavior for other installations.
- Decoder override is deliberately narrow: only a VP9 stream whose cached probe reports an alpha tag uses `libvpx-vp9`, and only an alpha-tagged VP8 stream uses `libvpx`. Ordinary WebM and other inputs retain FFmpeg's native/default decoder choice, avoiding a broad CPU-cost change. Decoder-side **Fit** supplies transparent-black padding for those alpha streams so the retained alpha is not replaced by an opaque matte.
- Delayed and offline AutoClip video/audio decoders receive output bounds equal to the remaining clip phase plus a small endpoint guard, with `-stream_loop -1` only when **Loop selected file** requests it. A non-looping zero-delay live selection instead reserves up to one second of actual source media after its visible window, capped at 20% of the source in addition to the separate endpoint guard. It never forces looping or rewinds to fabricate continuation.
- Live decode FPS defaults to the configured scene presentation rate. The live filter is `fps='if(gt(source_fps,0),min(source_fps,CAP),CAP)'` and runs before scale/crop, so a 60 fps source in a 30 fps scene stops generating roughly half of its otherwise discarded BGRA pipe traffic and scaling work, while a source whose reported rate is 23.976/24 fps is not upsampled. Unknown/zero source rate falls back to the cap and can therefore be normalized to that cadence. Explicit 30/15 choices remain lower ceilings. All live direct-file, YouTube, sequence, and AutoClip video uses output `realtime` pacing and no input `-re`. With a live cap, `realtime` uses `limit=3/effective output FPS`, rebasing after about three frames when a blocked stdout consumer resumes instead of replaying the entire wall-clock debt. Direct-file/YouTube and sequence clocks plus optional audio stay gated after initial open, resume, or restart until a genuinely fresh frame token arrives. Live audio first normalizes to 1024-sample, 48 kHz filter frames and then uses `arealtime=limit=0.1`, keeping low-rate source packets valid while preserving the same bounded-rebase property. Offline rendering remains unthrottled, omits live pacing, and runs scale/crop first and then applies the exact export FPS.
- AutoClip starts exactly one successor up to one second before a zero-delay live boundary while the outgoing session remains visible and keeps publishing changing frames. Hidden predecode advances the successor through its media, but only decoded media age beyond the selection's real trailing continuation reserve is charged against its visible phase. At the boundary, a ready successor receives publication, clock, and audio ownership together, and the outgoing process receives an immediate termination request before the shared disposal worker finishes cleanup. In live mode, the newest frame from each two-entry queue is still presented and genuine wall time since decoder output during a later UI stall is charged against the phase, leaving at least 50 ms. The pause path used by effective source disable stops both the AutoClip clock and decoder, freezing phase/fade, playback/audio activation, and the startup deadline. Resume re-arms that activation gate per decoder generation: a retained old frame cannot release it, and a fresh frame restarts the clocks with any post-output queue age still deducted. If another pause or an offline-render transition interrupts that open, the already-spent unpublished warm-up is settled into the hold before the generation is discarded, so repeated resumes cannot truncate the clip. A positive fade keeps the outgoing phase transparent until the new first-frame fade-in, while a positive delay clears it and uses the sequential path. If a cold open exceeds the outgoing selection's finite real tail, natural EOF can fall back to its retained last good frame until the successor is ready.
- Applying an unchanged AutoClip path/timing configuration no longer resets its schedule. Fit-mode changes restart FFmpeg only when the decoder itself performs the exact crop/pad/scale; compositor-only fit changes keep the current process because its command is unchanged.
- Replaced AutoClip and sequence sessions are disposed by one reusable background media worker. Shutdown explicitly walks source-owned sessions, drains that queue for a bounded interval, and then performs manager-wide child termination. This replaces one newly created OS thread per handoff and closes the ownership gap for sessions that were not stored in the ordinary path-keyed capture registry.
- Live recording submission uses a bounded, nonblocking encoder queue instead of stalling the render/UI thread when an encoder falls behind. Offline rendering can wait briefly for queue capacity because it is throughput-oriented. Recorder drain and FFmpeg finalization have deadlines, and app shutdown explicitly aborts the active encoder before the manager-wide process sweep, so a blocked pipe write cannot prevent orphan cleanup.

LifeViz intentionally does not introduce a library-wide warm decoder pool or persistent transcode/frame cache. The only overlap is the active outgoing clip plus one already-selected cold-opening successor during the one-second zero-delay live lookahead. It is capped at two owned/tracked AutoClip video decoders, with an immediate outgoing termination request at boundary promotion and one remaining after cleanup. Delays and offline rendering remain sequential. Frames stay in the existing small in-memory stdout queues, and no handoff media or staged transcode is written to disk. A reusable pool large enough to cover random libraries would retain CPU threads, process working sets, pipes, and decoded buffers; a disk cache would add exactly the sustained writes this pass is designed to avoid. Longer configured clip durations remain the direct way to reduce necessary random-input process starts when that behavioral tradeoff is acceptable.

Transparent WebM support stays inside that boundary: it extends the existing cached probe result and continues streaming raw BGRA over stdout. It adds neither a second metadata process nor a persistent media writer/cache.

The `config-save-coalescing` smoke test exercises burst, duplicate, changed, and shutdown persistence behavior. `gpu-source` covers the D3D source compositor, while the current-scene profiling targets measure the complete saved stack.

The `ffmpeg-lifecycle` smoke starts a controlled FFmpeg child through an isolated manager, verifies that it is tracked and receives the external temporary working directory, closes the manager/Job Object, and fails if the child remains alive. It is the focused regression test for orphan-process containment, update-safe process startup, and direct executable resolution.

The `webm-alpha <path>` smoke is the complementary correctness gate for an alpha-tagged VP8/VP9 WebM. It exercises the cached metadata probe and first-frame BGRA decode, verifies the selective `libvpx` plan retains non-opaque alpha, and guards transparent **Fit** padding without creating a persistent test cache.

The `live-video-audio <path>` smoke pauses a real direct video, proves its public clock remains held through resume until a new-generation frame token is published, then injects deterministic FFmpeg deadline debt and verifies output pacing rebases instead of repaying that full interval as a burst. It also covers the normalized live `arealtime=limit=0.1` audio path.

The `autoclip <path>` smoke exercises offline scheduling/audio/fade behavior plus the unified live output-pacing plan and bounded overlap. It verifies no live input `-re`, the capped three-frame `realtime` limit and cached source-FPS parsing, expected realtime/arealtime warning suppression, unchanged offline filter ordering, a playback clock held before initial publication and advancing afterward, repeated held decoder generations plus a genuinely fresh frame on resume, an active performance-triggered restart, and preservation of the remaining phase across interrupted warm-up. Its focused zero-delay case forces a tail-adjacent non-loop selection and `100 ms` promotion delay for three consecutive handoffs, requires a moving `FramePublishTimestamp`, limits maximum stale publication to `300 ms`, caps owned/tracked sessions and newly observed FFmpeg PIDs at two during a seam, requires one session afterward, and verifies final cleanup. It creates no library-wide prewarm, persistent media cache, transcode, or disk output.

The application's core logic has been significantly optimized to improve performance, especially on multi-core systems. Several key parts of the application that perform heavy computations over large collections of data now run in parallel. This allows for larger grid sizes, more complex scenes with multiple sources, and higher frame rates.

The following components have been optimized by converting their sequential `for` loops into parallel operations using `System.Threading.Tasks.Parallel.For`, which distributes the workload across available CPU cores.

### Core Simulation (`GameOfLifeEngine.cs`)

-   **`StepChannel`:** The primary `Step` function, which calculates the next generation for every cell in the simulation, has been parallelized. The calculation for each row of the grid is now an independent task, allowing the engine to scale with the number of available cores.

### Rendering & Compositing Pipeline (`MainWindow.xaml.cs`)

The main rendering and compositing pipeline involves several steps that iterate over large pixel buffers. These have been parallelized:

-   **Source Compositing (`CompositeIntoBuffer`, `CopyIntoBuffer`):** When multiple video or webcam sources are active, the process of resizing and blending them into a single composite image is now performed in parallel. Each row of the destination buffer is processed independently.

-   **Color Buffer Generation (`EnsureEngineColorBuffer`):** The process of converting the raw `(true/false)` state from the simulation engine into a displayable color buffer has been parallelized.

-   **Injection Mask Generation (`BuildLuminanceMask`, `BuildChannelMasks`):** The methods responsible for creating boolean masks from the composited input sources are now parallel. These masks determine how external video feeds influence the Game of Life simulation.

-   **Final Render & Effects (`RenderFrame`, `InvertBuffer`):**
    -   The final step of copying the computed simulation state into the buffer that is displayed on the screen has been parallelized.
    -   The `InvertBuffer` effect, which inverts the colors of a buffer, has also been updated to run in parallel.
