# Rendering Pipeline

## Layout

- `Bitwise RGB` is implemented as a third Conway life mode, not as a separate effect layer. On the live GPU path it quantizes the sampled RGB input to bytes, injects every `1` bit into its corresponding Conway plane, then reconstructs output RGB bytes from the 24 evolving planes.

- `MainWindow.xaml` hosts a `Viewbox`-wrapped render host so the simulation keeps a constant aspect ratio. Default is 16:9, but the first aspect-bearing visual source in the *Sources* stack overrides the ratio automatically. Color Planes are output-relative and skipped during aspect selection, recursively including groups whose descendants are only planes; a plane-only scene uses the normal 16:9 fallback.
- The logical output surface is still sized to the current simulation grid (`columns x rows`), so each logical cell maps to a single pixel before scaling; that surface is presented either through a D3D11 `DrawingSurface` (preferred) or the legacy `WriteableBitmap` fallback.
- Presentation is now routed through a dedicated WPF CPU presentation backend (`WpfPresentationBackend`) that owns surface allocation, passthrough underlay presentation, shader-fallback effect state, and final pixel upload.
- CPU source compositing is also isolated into its own component (`CpuSourceCompositor`) instead of being embedded directly inside `MainWindow`.
- `MainWindow` now addresses rendering through an explicit `IRenderBackend` contract. The default startup path attempts `GpuRenderBackend` first, which swaps the XAML image host to a `Vortice.Wpf.DrawingSurface`, uploads simulation/underlay buffers into D3D11 textures, resolves the final passthrough composite in a fullscreen GPU shader pass, and now also prefers a D3D11 source-composite pass for `BuildCompositeFrame`; `CpuRenderBackend` remains as migration fallback.
- Final simulation-layer compositing now also prefers a dedicated D3D11 fullscreen pass in `GpuPresentationBackend` when not recording. Active simulation layers are presented with per-layer blend mode/opacity metadata, and the old CPU per-pixel blend in `MainWindow.RenderFrame()` remains as the fallback path for unsupported cases and recording.
- The render host (`Viewbox` / `RenderSurfaceHost` / `DrawingSurface` fallback image) is explicitly non-hit-testable. Mouse input should bypass the presentation surface and land on the window/root context-menu layer instead of forcing WPF to interact with the GPU host on hover.
- Simulation layers now target an `ISimulationBackend` contract, but the runtime implementation is now GPU-only: `GpuSimulationBackend` is required at startup and the old `CpuSimulationBackend` fallback has been removed.
- `GpuSourceCompositor` and `GpuSimulationBackend` now share a single D3D11 device/context (`GpuSharedDevice`) so the source composite can be handed straight to either grayscale or RGB simulation layers as a shader resource instead of forcing a CPU mask rebuild first.
- Embedded `Sim Group` output crosses into WPF presentation through a three-slot, two-sided snapshot lease. The producer permits one snapshot copy in flight and does not publish its slot until a producer event query completes. The WPF presentation device then copies that shared snapshot into a private underlay and may retain up to three consumer reads; each producer slot remains leased until its consumer event query completes. Polling is nonblocking, ring handles are cached for the resource generation, and saturation holds the previous private frame instead of publishing prior slot contents or falling back to the live mutable shared surface. That specifically prevents the clean whole-scene rewind by one ring rotation that previously appeared as a short skipback. The lease protocol applies to this inline snapshot handoff, not to every legacy non-inline shared texture.
- Native-source preference is now differentiated by media type. Static file sources can return to native frames at moderate output sizes, but video file sources and video sequences stay on adapted/direct decoder output across the preset ladder. The earlier video-native fallback was the point where `1080p+` underlay freshness collapsed even when render/sim timing still looked acceptable.
- `GpuSourceCompositor` now explicitly unbinds its composite render target before returning that texture to the simulation backend. This avoids a D3D11 SRV/RTV hazard that could otherwise make RGB composite-threshold injection sample black even when the source composite itself was correct.
- The scene-layer scale UI maps its left half linearly across `0.10×`-`1.00×` and its right half across `1.00×`-`4.00×`, with a small center detent resolved to exactly `1.00×`. Both slider and numeric entry update the same persisted `CaptureSource.Scale`; the CPU and GPU compositors combine that centered base transform with animation transforms before fit-mode sampling, so live playback and fixed-duration renders share the result. Inline `Sim Group` output normally stays on its zero-copy handoff, but a non-neutral group scale adds one source-compositor pass around the resolved group surface (or the equivalent CPU copy/transform) so the special inline branch honors the same control.
- Smoke-test startup now runs under `App.IsSmokeTestMode`, which still constructs the real WPF window/render backends but skips persisted project load, media/file/window source startup, ffmpeg decode, and audio-loopback initialization so startup regressions can be tested without booting the full user scene.
- Normal startup distinguishes a current-version empty scene from both a missing/unusable config and an unversioned empty config left by the earlier black-screen startup path. Missing/unusable and legacy-empty configs take the starter fallback: `MainWindow` creates a scene-stack `Sim Group` containing the default randomized `Life Sim`, compiles that group into the runtime simulation layers, writes the current config-version marker, and queues the resulting scene for persistence before the render loop starts. Current-version empty scenes remain empty, so clearing the scene after migration does not resurrect hidden simulation layers on later launches.
- Main window shutdown now stops the background frame timer and swaps to a null render backend before disposing GPU/CPU render resources, so teardown does not race a final UI-frame callback against already-freed backend state.
- The GPU presentation backend also exposes smoke-test counters so `--smoke-test gpu-render` can assert that the fullscreen composite shader path actually initialized through `MainWindow`, not just that a hidden window opened successfully.
- The GPU source compositor also exposes smoke-test counters so `--smoke-test gpu-source` can assert that `BuildCompositeFrame` actually ran through the D3D11 path instead of silently falling back to CPU.
- `--smoke-test chroma-key` checks exact green, blue, and red keys through both compositors and requires real GPU source-composite passes, catching red/blue channel-order regressions that a green-only CPU test cannot see.
- `--smoke-test gif-source-recovery [path.gif]` verifies that GIF setup is nonblocking, playback content changes through the bounded streaming session, resident raw buffers stay capped, removal completes promptly, and corrupt GIF data reaches a terminal error and removable session state. Without a supplied path it generates a deterministic animated GIF for the test; a path or `LIFEVIZ_SMOKE_GIF` exercises the valid-file checks against reported media, and `all` includes the generated case.
- `--smoke-test gpu-handoff` verifies that the GPU source composite can inject directly into the GPU sim path through `MainWindow` and that the composite frame carries zero CPU readback bytes for that test.
- `--smoke-test gpu-rgb-threshold` specifically validates the RGB composite-threshold injection path with a pure-white source and fails unless all three RGB channels inject successfully.
- `--smoke-test passthrough-underlay-only` now drives the real frame tick for the zero-layer passthrough case: when all simulation layers are disabled, source capture/composite refresh must still happen and the final frame must still present the source composite instead of dropping to black.
- `--smoke-test gpu-frequency-hue` validates the per-layer frequency-driven hue path numerically: it checks that changing dominant frequency changes the hue metadata sent to final composition while the raw RGB simulation buffer remains unchanged on the live GPU path.
- `--smoke-test simulation-reactive-mappings` validates the modular per-layer mapping system directly: it checks `Level -> Opacity`, `Level -> Framerate`, `Frequency -> Hue Shift`, `Injection Noise`, `Threshold Min`, `Threshold Max`, and `Hue Speed` against known normalized audio inputs, and it does so with the legacy global audio-reactivity master toggle forced off so per-layer mappings cannot silently depend on the old global gate.
- `--smoke-test simulation-reactive-persistence` round-trips per-layer reactive mappings through both the scene-project serializer (`LayerConfigFile`) and the app-config normalization path, so save/load regressions in the new mapping system are caught automatically.
- `--smoke-test simulation-reactive-legacy-migration` verifies that old whole-scene `Level -> Framerate` / `Level -> Life Opacity` settings are converted into per-layer mappings and that the legacy flags are cleared afterward.
- `--smoke-test gpu-injection-mode` validates that the GPU composite-injection path still distinguishes `Threshold`, `Random Pulse`, and `Pulse Width Modulation` on a mid-gray source instead of collapsing them to the same result.
- `--smoke-test gpu-file-injection-mode <video>` runs that same injection-mode density check against the first decoded frame of a real file source, which is useful when synthetic sources do not reproduce a report.
- `--smoke-test sim-group-inline-presentation` now uses the minimal inline flicker repro scene directly: rainbow background, inline `Sim Group` with `Pixel Sort`, and a portrait-like source above it at `240p`. The dynamic phase requires the presented output to keep advancing with the evolving scene, the static phase fails unless the presented frame stays bit-stable for the entire dwell window, and the redraw-pressure phase repeatedly invalidates the chrome/UI path while manual redraw requests and frame submits keep running, failing unless the presented frame stays stable with zero inline GPU-present fallbacks. It also includes a real file-backed `480p` hover phase and an exact-repro `480p` phase that uses the copied rainbow JPG plus converted Mona Lisa PNG from `Assets/SmokeRepro`. That exact phase keeps the real three-layer stack static and fails unless both the resolved inline composite and the presented frame remain bit-stable through hover/input pressure. The smoke now also asserts that inline scenes are handed to presentation through the dedicated GPU snapshot ring rather than directly through a live source-compositor shared texture. That catches GPU-timing/shared-surface regressions where counters still look healthy but the visible scene flickers or drops updates during hover/input activity.
- `--smoke-test gpu-snapshot-order` adds the ordering gate that the repeating visual smoke cannot prove. An opaque Normal overlay encodes a monotonically increasing 24-bit frame ID across every pixel above an inline Sim Group; the test submits 120 frames, adds redraw invalidations, and forces both producer- and consumer-query not-ready paths until the consumer ring saturates. Duplicate/held IDs are allowed, but backwards, future, or internally torn IDs fail. It also requires bounded lag and presentation progress, at least two rotating producer handles, held submissions under pressure, sufficient consumer occupancy and lease retirement, a final drain to zero active consumer queries, a paced phase without systematic extra redraws, and opened-resource counts bounded by the distinct-handle cache allowance. This smoke is part of the combined GPU UI suite run by `--smoke-test all`.
- The inline sim-group snapshot ring now publishes one frame behind the copy: each frame's composite is copied into a ring slot with a D3D11 event query marking its completion, and the slot actually handed to WPF presentation is the one copied on the previous frame, whose query has had a full frame interval to complete. The ring's shared NT-handle textures carry no keyed mutex, so before this change the WPF-side device could sample a slot before the producer's copy landed and draw the slot's previous content — one full ring rotation (3 frames, ~100 ms at 30 fps) old. Hover/invalidation-driven extra composition passes hit that race routinely and made the whole presented feed visibly skip backwards. The completion check returns immediately in steady state, so the frame loop never blocks on GPU work; the only synchronous wait is the first snapshot after startup or a resize.
- `--diagnostic-test current-scene-rewind-detect` (and `current-scene-rewind-detect-hover` with synthetic chrome hover pressure) loads the real saved scene, signatures every presented frame for 75 seconds, and fails if any presented frame repeats content shown earlier with different frames in between — direct detection of backwards-presented output. It also reports which inline present branch produced every frame (`gpuOk` / CPU fallback / no GPU surface / fell through) so a regression can be attributed immediately.
- `--smoke-test gpu-pixel-sort` validates the GPU pixel-sort backend directly. It injects a live GPU composite into the pixel-sort layer backend and fails unless the published output surface measurably differs from the input pattern while preserving the exact pixel histogram.
- `--smoke-test gpu-bitwise` validates the `Bitwise RGB` Conway mode directly on the GPU path. It injects a live GPU composite into the 24-plane backend and fails unless the rendered output reconstructs the expected RGB byte pattern from those bit planes.
- `--smoke-test sim-group-pixel-sort-color` validates the full inline scene-stack path for `Pixel Sort`. It fails unless a `Sim Group` with a `Pixel Sort` child still preserves the source histogram after the real sim-group compositor runs, which catches wrong-SRV-format bugs and underlay-double-add regressions that the raw backend smoke would miss.
- `--smoke-test pixel-sort-reactive-cell-size` validates that `Pixel Sort` reactive mappings can drive `Cell Width` / `Cell Height` all the way through the live GPU backend. It fails unless the runtime cell size changes and the resulting sort still preserves the source histogram.
- The combined `--smoke-test all` suite starts with the generated bounded-GIF recovery check, drives corrupt GIF data through real hidden-window scene removal plus isolated config persistence, then verifies the GPU simulation and passthrough-underlay/source/render UI paths.
- `--smoke-test gpu-benchmark` uses the same counters plus direct timing around `GpuSimulationBackend` to separate GPU source-composite upload/draw/readback cost from GPU sim inject/step/fill cost, which is useful for deciding whether the next optimization should target readback elimination or more sim work on GPU.
- `--smoke-test profile-mainloop` runs the real background-timer frame loop on a hidden synthetic scene and captures stage timings for capture/composite/inject/step/render/present plus dispatcher input/background latency samples. It also records frame-gap spike metrics (`frame_gap_over_25ms`, `frame_gap_over_33ms`, `frame_gap_over_50ms`) so pacing regressions can be separated from average throughput problems. Profile/pacing smokes now disable smoke-only CPU fallback color-buffer capture for GPU simulation layers, so render timings reflect the live shared-texture path instead of the correctness-validation path. Normal app runs export JSON reports under `%LOCALAPPDATA%\lifeviz\profiles`; smoke-test runs export under `bin\Debug\net9.0-windows-sbx\profiles\`.
- `--smoke-test profile-240` / `profile-480` pin that profiler to grayscale scenes at fixed resolutions, while `profile-rgb-240` / `profile-rgb-480` force the reference simulation layer into `RGB Channel Bins` so RGB-path regressions can be measured directly.
- `--smoke-test profile-file-240 <video>` / `profile-file-480 <video>` swap the synthetic source stack for a real file-backed source so decode/playback jitter can be profiled with the same stage timing pipeline. `profile-file-rgb-240 <video>` / `profile-file-rgb-480 <video>` do the same with the reference simulation layer pinned to `RGB Channel Bins`, which is the closest built-in smoke to the user's "real media + RGB simulation" workload. The video path can also be provided through `LIFEVIZ_SMOKE_VIDEO`. These file-backed smokes now fail if the file source does not publish enough fresh frame tokens, which catches freezes in the non-exact file-video handoff path automatically.
- `--smoke-test profile-current-scene` and `profile-current-scene-visible` load the persisted user config instead of a synthetic smoke scene, which is the correct profiling path once a performance problem only reproduces on the real saved stack. The visible variant keeps the normal desktop-composed window path alive so frame-pacing failures can be measured without manually reading the overlay.
- `--smoke-test profile-current-scene-fullscreen` extends that same real-scene path into fullscreen and now also validates the presented layout bounds, so the old "tiny centered/top-centered render rectangle" fullscreen failure is caught automatically instead of only by eye.
- `--smoke-test profile-current-scene-<144|240|480|720|1080|1440|2160>`, the visible variant, and the fullscreen variant force the real saved scene to a specific preset height before profiling, so a 720p-only or 1440p-only regression can be measured directly in the same presentation mode where it occurs.
- `--smoke-test profile-current-scene-presets`, `profile-current-scene-visible-presets`, and `profile-current-scene-fullscreen-presets` now sweep the full preset ladder from `144p` through `2160p`, which is the right baseline for tracking whether the app can realistically climb toward `4K`. The preset suite uses a shorter dwell per resolution than the single-target profiles so the whole ladder can run as a practical regression check.
- `--smoke-test profile-current-scene-interaction` extends that visible real-scene path by opening the Scene Editor, verifying that the main window does not remain interaction-throttled while the editor is open, then cycling the root context menu and comparing pre/editor/post frame-gap metrics so interaction-specific pacing regressions are caught automatically instead of being reproduced manually.
- `--smoke-test pacing-current-scene-visible-presets` and `pacing-current-scene-fullscreen-presets` turn pacing into a real pass/fail gate instead of a profile you have to interpret manually. They pin the real saved scene to a stable `60 fps` budget, sweep the realtime preset ladder (`144/240/480`), and fail if any run violates the configured frame-gap budget (`avg`, `p95`, `p99`) or underrun ratios (`frame_gap_over_25ms`, `frame_gap_over_33ms`, `frame_gap_over_50ms`).
- `--smoke-test pacing-current-scene-interaction` applies those same hard pacing checks to the `480p` Scene Editor/context-menu interaction case, and `pacing-current-scene-suite` bundles the visible preset ladder plus that interaction case into one regression pass.
- `--smoke-test pacing-current-scene-overlay-fullscreen-144` applies the same hard pacing gate with `Show FPS` enabled in fullscreen at `144p`, so the WPF timing/audio diagnostics are tested as part of the render budget instead of only by eye.
- `--smoke-test frame-pump-thread-safety` opens the real Scene Editor and then evaluates frame-pump interaction state from a worker thread. That catches cross-thread WPF access regressions in the timer-driven scheduler, including the `Window.IsActive` crash introduced by the custom-chrome frame-pump rewrite.
- GPU simulation-layer presentation now prefers shared D3D11 sim textures for both `Naive Grayscale` and `RGB Channel Bins`. CPU color-buffer readback is kept only for fallback, recording, or smoke-test verification paths.
- Audio analysis is no longer unconditional. The audio thread now skips waveform-history capture, 30-second debug-trace retention, and FFT/spectrum extraction unless the FPS/debug overlay is visible or a live feature requires spectral data (`Audio Granular` source animation or a simulation layer with reactive mappings that consume spectrum/band inputs). When those features are inactive, the app still computes the cheap envelope/beat signals needed for `Level -> FPS`, `Level -> Life Opacity`, and reactive seeding, but it avoids the heavier debug/spectrum work.
- When spectral data is needed, FFT/spectrum extraction is decimated to roughly `60 Hz` instead of running on every audio callback. The detector holds the last spectrum result between updates, which keeps `Audio Granular` and per-layer band/frequency mappings live while reducing audio-thread CPU cost and jitter.
- Live profiling now records finer-grained source capture timings too: `capture_window_frame_ms`, `capture_webcam_frame_ms`, `capture_sequence_frame_ms`, `capture_file_frame_ms`, and `capture_group_composite_ms`, in addition to the broader `capture_sources_ms` and `inject_capture_ms` buckets. That makes it possible to identify whether "inject/capture is slow" is really decoder acquisition, nested group composition, or later injection work.
- Live profiling now also records delivered file-video freshness directly: `capture_file_fresh_frame_ratio` and `capture_file_frame_age_ms` (plus sequence equivalents). That makes it possible to tell whether a "smooth sim, slideshow video" report is a stale-video problem or a render-pacing problem.
- Live profiling now also records per-source file-video freshness/age metrics using the source filename as a suffix. That matters when one file source freezes while another keeps updating, because aggregate freshness can still look acceptable in that mixed case.
- Current-scene profile smokes now wait through a warmup period and then validate the settled run against those freshness metrics. That change matters because startup/reconfigure noise can otherwise make a scene look healthy in smoke while it is still slideshowing in steady use.
- Profile and pacing smokes disable smoke-only CPU fallback-buffer readbacks for inline GPU source/simulation composites. Their timing therefore represents the normal shared-GPU presentation path instead of synchronizing the GPU solely to make test-inspection buffers available.
- The interaction profile derives its Scene Editor and recovery limits from the pre-interaction cadence. A saved 30 fps scene is therefore compared with its roughly 33 ms frame budget instead of being incorrectly failed against fixed 60 fps-era 25/35 ms thresholds.
- `--diagnostic-test` complements those smokes by running the normal saved-scene startup path instead of `App.IsSmokeTestMode`. Use it when smoke startup looks healthy but a real launch still diverges. The current diagnostic targets cover visible preset runs, fullscreen preset runs, interaction profiling, and a longer `720p` soak, and they write reports into the active build output's `profiles\` folder.
- Settled smoke/diagnostic validation now also checks `presentation_draw_fps`, not just frame-loop gap metrics. That closes the old gap where the app could report a healthy loop cadence while the actual presented surface was visibly stale.
- File-video sessions now start their decode worker on the first real capture request instead of immediately after probe. That ensures the worker starts once with the actual requested process mode (exact target vs adaptive/native) instead of launching a native-path worker and then immediately restarting it into a different mode.
- Long-lived file-video raw decode, sequence disposal/advance, and source-audio decode workers run away from the UI thread. Direct videos are added in a pending state instead of synchronously probing on WPF. Metadata probes use a capped, metadata-aware process-wide task cache with a maximum of two concurrent `ffmpeg` processes and one 15-second queue/process deadline, so a large sequence or AutoClip list cannot create one blocking worker and subprocess per file at startup. Cached results include source FPS alongside duration, dimensions, codec, and alpha metadata, so output pacing does not launch a second probe.
- Long-lived GIF/file-video raw decode, sequence disposal/advance, and source-audio decode workers run away from the UI thread. GIFs and direct videos are added in a pending state instead of synchronously probing or expanding animation frames on WPF. Metadata probes use a capped, metadata-aware process-wide task cache with a maximum of two concurrent `ffmpeg` processes and one 15-second queue/process deadline, so a dense GIF, large sequence, or AutoClip list cannot block startup.
- Long-running video/audio workers and spawned `ffmpeg` decoders run at normal priority by default. This keeps realtime frame reads and silent video-stack audio analysis from being starved when animation/compositing increases foreground render load. In **Low Contention Mode**, LifeViz stops requesting the global 1 ms multimedia timer, keeps the frame pump on a lower-priority thread, and moves decode work to below-normal/background scheduling.
- The root context menu exposes that behavior as a runtime tuning control. **Low Contention Mode** lowers LifeViz's process/frame-pump priority as well as media-worker pressure, **Decoder Threads** lets you cap `ffmpeg` decode fanout directly, and **Video Decode FPS** defaults to **Auto (scene FPS)**. Auto uses the configured presentation target as the cap and preserves a slower cadence when FFmpeg reports a valid source rate; an unknown/zero `source_fps` falls back to the effective cap rather than yielding zero output. Explicit `30`/`15` values are lower ceilings. The live `fps` filter precedes scale/crop so surplus frames are discarded before expensive transforms, while offline export applies the direct transform first and then its exact export-FPS filter. All live direct-file, YouTube, sequence, and AutoClip video uses output `realtime` pacing and no input `-re`. When a live decode cap is active, the pacing discontinuity limit is `3 / effective output FPS` (where effective output FPS is the known source cadence capped by the setting, or the cap when source FPS is unknown), so a blocked stdout pipe rebases after about three frames rather than repaying an arbitrarily long read-rate debt as a burst. Direct-file/YouTube and sequence playback clocks plus optional audio remain gated after initial open, resume, or decoder restart until that generation publishes a genuinely fresh frame token. Deterministic offline rendering uses no live pacing filter. `Auto` decoder threads remain bounded to two per live video, while offline export retains ffmpeg's full automatic fanout. Those settings are persisted and are applied to existing file/video/sequence/AutoClip sessions immediately by restarting their decode workers with the new limits.
- `--smoke-test dimensions` applies a real simulation height/depth change through `MainWindow`, forces the reference simulation layer into `RGB Channel Bins`, then drives the Scene Editor height dropdown in both Live Mode and deferred Apply mode, and fails unless every simulation layer plus the presentation surface height update together. It also validates project-FPS propagation, automatic and explicit decode-cap resolution, and the generated filter plans: the unknown-rate-safe live `fps` expression must precede scale/crop, while offline scale/crop must precede the exact export-FPS filter. This is command/filter construction coverage rather than a real-media decode test.
- `--smoke-test source-reset` clears the source stack, preserves passthrough state, re-adds a synthetic source, and fails unless the source composite is visible again after the stack comes back.
- `--smoke-test shutdown` opens and closes the real window, then fails if `MainWindow` captured any teardown exception during close.
- Simulation-layer render settings are now owned per leaf layer: each leaf carries its own life mode, binning mode, injection noise, life opacity, RGB hue offset, RGB hue speed, threshold window, and a list of reactive mappings. Those leaf stacks are now authored from `Sim Group` items embedded in the main scene tree instead of from a separate editor-only simulation tree. A separate global life opacity remains as a master multiplier across all simulation layers.
- Height selection is preset-driven (`144`, `240`, `480`, `720`, `1080`, `1440`, `2160`) in both the root context menu and the Scene Editor, so grid resize uses the same row-count choices everywhere.
- `--smoke-test shutdown` now opens the Scene Editor before closing the real main window, so owner/owned-window teardown regressions are caught too.
- CPU fallback pieces are now limited to source/presentation seams. Source compositing still has a CPU fallback path, but simulation itself no longer keeps a second CPU backend alive.
- Simulation backends can now share a GPU-surface contract instead of assuming Conway-specific state. `GpuSimulationBackend` still owns life stepping; `GpuPixelSortBackend` is a GPU-only effect backend that snapshots the latest upstream composite, resolves a full per-step cell sort on-GPU, and publishes that sorted color surface back into the same sim-group chain.

## Simulation Loop

- A coalesced one-shot background timer now drives the frame loop in `MainWindow.xaml.cs`; simulation stepping still starts from the selected framerate (15 / 30 / 60 / 144 fps), optional FPS oscillation, and optional global audio-reactive FPS boost, but enabled simulation layers now keep their own effective target FPS and their own step accumulators.
- A dedicated high-resolution frame-pump thread now owns cadence. Instead of relying on `System.Threading.Timer`, the scheduler thread tracks the next target presentation time with `Stopwatch`, uses a coarse sleep plus fine spin for the last sub-millisecond slice, and posts at most one pending frame callback to the dispatcher at a time. The dispatcher callback normally runs at `Render` priority, and the cadence state is explicitly reset after native move/resize throttling or a simulation-dimension change. That substantially reduces baseline underruns and timer-queue jitter without going back to `CompositionTarget.Rendering`. The actual frame work still runs on the WPF UI thread, and LifeViz now reserves interaction throttling for true native move/resize loops instead of automatically dropping to a low-rate/background-priority path just because the root context menu or Scene Editor is open.
- Any interaction state that the background timer needs is now cached into thread-safe fields on the UI thread first. The timer thread no longer reads WPF-owned properties such as `Window.IsActive` directly, which avoids cross-thread `InvalidOperationException` crashes.
- Source capture/composite refresh is now decoupled from simulation stepping. `MainWindow` refreshes the source stack every render tick, then only injects into simulation layers on frames where a layer actually needs a step. That keeps passthrough and file/video underlay smooth even when no simulation layers are enabled or when a layer's effective sim FPS is lower than render FPS.
- Shared GPU sim/underlay presentation now performs one synchronized producer flush at the final handoff into `PresentSimulationComposition(...)` whenever shared producer resources are actually in play. That avoids the stale-shared-texture case where the sim appears to update at ~1 FPS visually even though the frame loop and simulation-step counters are still advancing.
- Inline `Sim Group` scenes still resolve through the shared-GPU presentation path, and `MainWindow` now emits a throttled warning if that inline GPU handoff falls back to the CPU-present path. That gives live repros a concrete signal in the app log when the shared-surface handoff itself is failing instead of forcing blind renderer changes.
- GPU blend/effect state changes invalidate the presentation surface only when the state actually changes. Normal frame submission already requests a draw, so unchanged per-frame blend updates no longer add a second unsynchronised invalidation beside the new logical frame.
- GPU source-layer compositing now defaults to point-sampled texture reads rather than linear filtering, so ordinary image/video layers stay pixel-sharp by default instead of picking up implicit smoothing just because they passed through the GPU compositor.
- The main output window now removes the native non-client title bar entirely (`WindowStyle=None`, `ResizeMode=NoResize`) and replaces it with custom chrome plus manual pointer-driven move/resize zones. That means ordinary window dragging/resizing no longer enters the OS move loop, which is necessary if render cadence is going to be meaningfully decoupled from shell interaction. Native fullscreen still uses the separate fullscreen toggle path.
- Window movement is no longer limited to the chrome strip. The render background itself now participates in the same pointer-driven drag path, and double-clicking that background toggles fullscreen, so the output surface behaves like a projector-first canvas rather than a conventional titled window.
- Manual resize now owns aspect enforcement during the drag. `MainWindow_OnSizeChanged` no longer fights the custom resize path, so releasing a resize grip no longer snaps the window back to an old size.
- Entering or exiting fullscreen now explicitly resets frame-pump cadence as part of the mode switch, which prevents stale scheduler timestamps from poisoning the first steady-state fullscreen frames.
- Applying a new simulation height/depth now also clears the last composite cache, forces a surface rebuild, and issues an immediate redraw so a dimension change cannot remain visually stuck on an old frame until later activity arrives.
- Each simulation step (unless paused) captures every active source, composites them (per-source blend modes, ordered by the stack, including layer groups), then runs the simulation stack. Embedded `Sim Group` nodes now execute inline inside that same scene-stack walk instead of being compiled out into one final overlay stack. The first child in a sim group samples the composited scene surface that exists at the group's exact stack position, each later child samples the previous child output, and the group's resolved output is then fed forward to any lower scene layers. On the live GPU path, that inline interleaving now stays on the shared D3D11 device: regular sources append onto the current GPU scene composite, sim-group children still inject from upstream GPU surfaces, and the group's visible output is resolved by an offscreen GPU final-composite pass rather than by CPU pixel blending. To keep that inline path from degenerating into one compositor setup per ordinary source, contiguous non-sim scene layers are now batched back into a single GPU source-composition segment on each side of a sim group. CPU readback is retained only for explicit recording and smoke-validation paths, and the profiling smokes suppress intermediate sim-group readback so their timings stay closer to the live shared-texture path. Per-layer RGB hue shift is preserved on that offscreen pass using the same final-composite shader semantics as normal presentation, so inline sim groups no longer bypass hue rotation when they move into the main stack. `Pixel Sort` is treated as a standalone full-frame effect in that pass: once a pixel-sort layer has baked the upstream scene into its own output, the group compositor does not add the original underlay back on top of it. After injection, optional audio seeding (continuous level-based and/or beat-triggered) applies, enabled leaf layers advance once, then `RenderFrame()` runs. Injection no longer pushes an extra history slice before stepping, which keeps autonomous patterns crisp instead of duplicating them in the depth trail.
- A `Sim Group` with no visually active children is now treated as a pure passthrough. If every child resolves to zero effective opacity, the group no longer publishes its own intermediate composite or changes baseline selection; the upstream scene composite just flows through unchanged.
- When target simulation FPS exceeds the effective UI tick cadence, LifeViz runs multiple simulation steps per timer tick (bounded catch-up) so high-rate modulation remains visible in evolution speed.
- Only the first pass in a render frame performs source injection. Additional bounded catch-up passes remain step-only, so inline sim groups keep the same "inject once per render frame" behavior as standalone simulation layers while still respecting their main-stack position.
- The engine maintains a depth stack (`List<bool[,]>`) where index 0 is the newest frame.
- Clearing all sources no longer forces passthrough off. An empty source stack still renders black when there is no underlay to show, but the passthrough preference is preserved so re-adding sources restores underlay display immediately.
- On the GPU presentation path, the finished simulation frame is uploaded into a dedicated D3D11 texture, the passthrough underlay is uploaded separately when needed, and a fullscreen shader pass resolves the selected composite blend mode into the `DrawingSurface` color target. Source compositing can now also happen in D3D11, and the grayscale-GPU injection path can consume that composite directly without rebuilding CPU masks first. On the normal live GPU path, passthrough underlay now uses the shared GPU composite surface directly instead of forcing a CPU composite readback just for final presentation; CPU composite readback is still required for recording, for any simulation layer that falls back to CPU mask injection on that frame, and now also for the explicit zero-enabled-sim-layer path so the final frame cannot get stuck showing stale simulation output.
- The visible render host no longer wraps the presentation surface in a WPF `Viewbox`. The GPU `DrawingSurface` and fallback `Image` now scale with `Stretch=Uniform` inside a plain black host, which removes a large-window/fullscreen WPF scaling layer that could make video presentation look choppy even when simulation timing stayed healthy.
- `DrawingSurface` has no natural bitmap aspect of its own, so the GPU presentation backend now computes the displayed DIP rect explicitly from the sim-surface aspect and the current host size. That keeps fullscreen presentation filling the expected letterboxed/pillarboxed rect instead of collapsing to a square when WPF has only the host bounds to work from.
- The presentation pass no longer forces an explicit D3D context flush every frame. WPF interaction latency during window drag/menu use is highly sensitive to UI-thread GPU sync points, so presentation now queues work normally and lets the compositor pace it.
- Per-layer simulation backend ownership is now decoupled from `MainWindow`; removing/reordering layers disposes any orphaned simulation backend instances, which is necessary once layers start owning GPU resources instead of pure managed CPU state.
- `GpuSimulationBackend` now covers both life modes. In `Naive Grayscale`, the backend can inject in two ways: CPU-built masks upload into a D3D11 mask texture for fallback compatibility, or the preferred path samples the final GPU composite texture directly inside a compute shader using the layer's threshold window, direct/inverse input function, injection mode, PWM period, and injection noise. In `RGB Channel Bins`, the backend keeps the combined depth stack on GPU, injects either uploaded RGB mask textures or the final GPU composite directly, applies inverse hue-rotation mapping before channel gating, steps each channel slice independently on GPU, and renders the final RGB color texture there too.
- `InjectCaptureFrames()` keeps the common path GPU-only, but if a leaf layer needs CPU mask fallback on a frame where the composite was built without CPU readback, it now lazily rebuilds the composite once with CPU readback enabled and uses that for fallback injection. Sim-group chaining itself is intended to stay on the GPU path by handing downstream children the upstream child color surface directly. `GpuPixelSortBackend` now publishes two GPU surfaces for that reason: a normal BGRA color surface for downstream sampling/injection and a separate integer-formatted presentation surface for the legacy sim-layer final-composite shader path, so pixel-sort layers stay color-correct in both chaining and final presentation.
- Static file-backed image layers no longer opt into the native-source presentation fast path. They stay on the exact downscaled BGRA frame path, which keeps them pixel-stable during hover/input redraw pressure and avoids implicit smoothing on the default presentation path.
- On the normal GPU presentation path, grayscale GPU simulation layers now share their rendered color textures with `GpuPresentationBackend` through D3D11 shared-resource handles. Final simulation-layer compositing now also owns per-layer RGB hue rotation on the GPU: the CPU computes each layer's current hue `sin/cos` once, then the fullscreen final-composite shader applies that hue to the sampled layer texture before blend. CPU hue rotation is only retained for explicit CPU fallback cases such as recording.
- Shared GPU simulation textures are now submitted once per frame, not once per layer. `GpuSimulationBackend.TryGetSharedColorTexture()` no longer flushes the shared D3D11 context on every layer query; instead the main render path flushes the shared device once only when at least one shared simulation texture will actually be presented. That removes redundant UI-thread GPU sync points in multi-layer RGB scenes.
- The GPU simulation backend now has a runtime smoke test path. It validates D3D11 device/shader initialization, grayscale injection/step/render, RGB injection/step/render, binary/fill color-buffer output, and mode switching across both life modes.

## Color Encoding

- The depth is partitioned into three slices (R/G/B). If depth = 24, each slice gets 8 layers; remainders are distributed so `Depth % 3` spreads extra layers across R and G first.
- For each slice, the engine walks the relevant frames and treats alive cells as set bits, forming a binary number. That integer is normalized against the maximum for that bit-length to derive a 0-255 channel value.
- The grayscale GPU simulation backend reproduces that same slice math in its render compute shader, including both `Fill` and `Binary` binning, so grayscale output parity does not depend on per-cell CPU reads.
- In *RGB Channel Bins* mode, hue is resolved per simulation layer, not globally. Each layer's final hue is:
  - base `Hue Offset`
  - plus time-based `Hue Speed`
  - plus any reactive `Hue Shift` mappings (for example `Frequency -> Hue Shift`)
- Dominant frequency uses the same logarithmic note-scale normalization as the magenta debug trace, so equal musical intervals produce roughly even hue travel.
- RGB capture injection uses the inverse of that same per-layer hue rotation when building per-channel masks, remapping source colors into the rotated bin basis before mode-specific gating. This keeps channel activity aligned to the currently shifted palette.
- The renderer writes BGRA bytes into `_pixelBuffer` by compositing simulation layers in the configured simulation-layer order (editable in Scene Editor), each with its own blend mode; default stack is Positive (Direct/Additive) first, then Negative (Inverse/Subtractive) on top, then presents that buffer through the active render backend.
- For simulation-layer `Subtractive` blending, subtraction is performed against the already composited simulation pixel. With passthrough off, subtractive-only stacks use white as the baseline (subtractive identity). Additive+subtractive-only mixed stacks use a neutral gray baseline (50% normalization bias) so both layers stay legible when combined; other mixed blend families use black baseline. With passthrough underlay precomposited in-buffer, additive/subtractive-only stacks are resolved in a signed delta path, and mixed add+sub pixels apply underlay-aware headroom normalization before final clamp to reduce order bias and prevent cross-family washout.

Using ffmpeg for GIFs composes the logical canvas, frame offsets, and disposal operations correctly instead of stretching optimized subframes as full images.

It opens no window, camera, file, or decoder session and survives the capture walk without entering missing-frame removal. The cached pixel follows the same ordered CPU/GPU source and group compositing paths as other sources, including fit/scale/animation transforms, opacity, blend, and downstream `Sim Group` input.
2. GIF/file-video sessions keep a short queue of decoded raw frames plus a small reusable buffer pool instead of a single "latest frame" slot or an eagerly expanded animation. Brief UI/render stalls therefore consume buffered decoded frames on the next ticks instead of immediately overwriting unread frames. Decoder-sized GIF frames are handed directly to the compositor for scaling, avoiding synchronous per-animation-frame resampling on the WPF callback. Disabling the layer or a parent group suspends the streaming worker; removal tears it down promptly.
3. Scene Editor simulation-layer dropdowns bind to `LayerEditorOption` values, and `LayerEditorOption.ToString()` now returns the user-facing label. That keeps the selected value readable inside the custom dark ComboBox template instead of showing the CLR type name.
4. Each capture is downscaled to the grid size and stored as BGRA using the per-source fit mode (Fill default, plus Fit/Stretch/Center/Tile/Span); source downscale now uses small supersampled filtered sampling (2x2 taps over each destination pixel footprint) to reduce vertical/horizontal banding and aliasing in live imagery before injection, while buffers are still reused per window/webcam to avoid per-frame allocations. File-video downscale also avoids `Parallel.For` for small outputs, because low-resolution scenes spend more time in threadpool overhead than in the actual sampling work.
5. File-video downscale now short-circuits the common adapted-video cases before falling back to the supersampled sampler:
   - exact-size frames are copied directly
   - equal-width fill/center frames use centered vertical crop
   - equal-height fill/center frames use centered horizontal crop
   - equal-width/equal-height fit/center frames use centered pad copy
   These fast paths target low-resolution adapted decode outputs where the old supersampled per-pixel sampler was needlessly expensive and could leave underlay video visibly stale even while simulation/render timing looked healthy.
6. When a video layer does not need native source pixels and its fit mode is `Fill`, `Fit`, or `Stretch`, `VideoSession` now asks `ffmpeg` to emit exact target-sized BGRA frames directly only when that target still fits inside the native source bounds:
   - `Fill` uses `scale ... force_original_aspect_ratio=increase` plus `crop`
   - `Fit` uses `scale ... force_original_aspect_ratio=decrease` plus `pad`
   - `Stretch` uses direct `scale`
   In those modes, the decoded frame can bypass the CPU downscale worker entirely and publish straight to the compositor/injection path. If the requested preset would force decoder-side upscaling beyond native size, the session stays on adaptive/native decode and lets the GPU compositor do the upscale instead.
7. Even when a video session is not using exact target output, it now publishes its current decoder-sized frame directly into the compositor path instead of forcing a CPU resample to engine size first. That means adaptive/native video decode sizes can still stay fresh while the GPU compositor handles the final scale to the grid. The published frame also carries its true buffer dimensions through the capture path, so the compositor does not mistake a native/adaptive frame for an already-target-sized one. `CaptureFrame()` now returns those decoder-sized buffers as-is instead of discarding them for not matching the requested target size, which fixes the source-specific freeze where smaller videos would stop updating as soon as they left the exact-target decode path.
8. On `GpuRenderBackend`, sources are uploaded as D3D11 textures and composited in stack order on a GPU render target using the same fit modes, mirror handling, animation transforms, keying, opacity, and blend modes (Normal, Additive, Multiply, Screen, Overlay, Lighten, Darken, Subtractive). File/video-sequence sources can hand the compositor their decoder-sized frame directly, and the GPU does the final fit/scale work instead of the old CPU video resampler. The compositor uses point sampling by default so layers stay crisp, but DVD Bounce translation is snapped to whole pixels before compositing to reduce shimmer on moving photographic layers without re-enabling smoothing globally. The compositor uses a ping-pong render-target pair and can export the final composite as a shared D3D11 texture for direct grayscale-GPU simulation injection. On failure or unsupported initialization, it falls back automatically to `CpuSourceCompositor`. Layer groups still recurse through `BuildCompositeFrame`, so grouped composites benefit from the same GPU path when the backend is active.
9. File-video sessions now also adapt the `ffmpeg` decode/output size and rate to the current presentation target whenever native source pixels are not required. Instead of always decoding raw BGRA at native-ish resolution and native FPS, low-resolution scenes restart the file-video pipeline at a process size that preserves source aspect while covering the current grid. The live filter starts with `fps='if(gt(source_fps,0),min(source_fps,CAP),CAP)'`: it drops surplus frames before scale/crop, preserves a known slower native cadence, and uses the effective cap when the source rate is unknown instead of treating unknown as zero. Its final `realtime=limit=3/EFFECTIVE_OUTPUT_FPS` stage paces direct-file, YouTube, sequence, and AutoClip output at the selected/known cadence without input `-re`; when no cap supplies an effective cadence, plain `realtime` is used. A 30 fps scene therefore halves the scaled BGRA output of a 60 fps file without turning a known 23.976/24 fps movie into duplicate 30 fps frames, and a pipe stall does not create a full wall-clock catch-up run. Offline rendering reverses the transform order—direct scale/crop first, then exact `fps=EXPORT_FPS`—because deterministic export requires exactly that output cadence, and it omits the live pacing stage. Live workers map only the first video stream, use one filter thread for scaling, retain no more than two pending raw frames, and use two codec threads when **Decoder Threads** is `Auto`; this bounds oversubscription, pipe bandwidth, and stale-frame latency in movie-heavy scenes.
10. File-video restarts now preserve the last published frame while the new `ffmpeg` worker spins up. Without that, a size change like `480p -> 1080p` could momentarily clear `_readyDownscaled`/`_readyRaw` and present black until the replacement decode stream produced its first frame.
11. Video-sequence layers keep presenting their last good frame while the next clip session is opened asynchronously. Sequence handoff is still a cold clip open today, but the compositor no longer drops to black just because the next clip has not produced its first decoded frame yet. Probe metadata is requested lazily through the shared two-process cache; live capture keeps presenting while that task completes instead of blocking the frame callback. Offline handoffs apply one deadline across candidate paths and render frames, then skip an unprobeable source for that export instead of appearing hung for minutes.
12. The GPU final-composite path no longer forces redundant producer-device flushes before every present. Shared underlay/simulation textures are still consumed through the GPU final-composite shader, but the hot path no longer synchronizes the producer device twice per frame, which was the main cause of the render-side `720p` stalls after source capture was fixed.
13. Inline scene-stack GPU presentation now snapshots the resolved inline composite into a dedicated three-surface GPU ring with a two-sided lease. On the producer device, `CopyResource` is followed by an event query and a flush; a slot is not published until that query completes. On the WPF presentation device, each published shared handle is opened once and cached for the current resource generation, copied into a private presentation texture, and associated with a consumer event query. The producer slot remains leased and cannot be selected for another snapshot until that consumer query reports completion and retires the lease. If producer completion is pending or all producer/consumer slots are occupied, the renderer holds the already-copied private frame and does not substitute the mutable live compositor surface. Query failure/timeout fails closed until presentation resources are reset. This protocol is scoped to the dedicated inline `Sim Group` snapshot-underlay handoff; legacy shared resources elsewhere in the renderer, including non-inline shared simulation handles, retain their existing copy path and are not covered by this synchronization claim.
14. The composited downscaled buffer feeds the injection path for every enabled simulation layer. Conway `Life Sim` layers still choose their own input function (Direct `y=x` or Inverse `y=1-rgb`), injection mode (Threshold/Random Pulse/Pulse Width Modulation), and threshold window (min/max + invert) before mode-specific gating. In **Threshold** mode, each layer's threshold window acts as a boolean gate. In **Random Pulse** and **Pulse Width Modulation**, that same window shapes injection intensity before probability/duty-cycle evaluation (including inverted windows), so threshold sliders influence all injection modes. `Pixel Sort` layers skip Conway injection entirely: they snapshot the upstream GPU composite directly, convert those sampled pixels into an exact byte-preserving GPU work texture, and then sort each configured cell in top-left-to-bottom-right order. Pixel Sort is now parameterized by `Cell Width` and `Cell Height`, not by grid counts; `1x1` is effectively passthrough because each cell contains a single pixel. Those cell-size parameters can also be driven by per-layer reactive mappings in the live GPU path. Every reactive mapping now has its own input `Min` / `Max` threshold window; the raw audio-driven value is normalized through that window to `0..1` before the mapping amount is applied. For `Cell Width` / `Cell Height`, the reactive amount is treated as an additive `+px` delta from the base cell size and is capped at `50 px`, because the filter stops behaving well once cells get too large. The publish step resolves that byte-preserved work texture back into the shared BGRA presentation surface so downstream layers and final presentation see the sorted image without a CPU round-trip. If a source disappears, it is removed automatically; removing the last source restores the default aspect ratio (and webcam capture is released).
15. On pure binary inputs, injection modes can legitimately converge. For example, with a threshold window of `0.5..1.0`, black maps to `0` drive and white maps to `1` drive, so Threshold, Random Pulse, and PWM all inject identically on those pixels. To verify that mode switching still works, use a mid-gray source or the `gpu-injection-mode` smoke test rather than a pure black/white pattern.

## Passthrough Underlay

- When **Passthrough Underlay** is enabled, the composited buffer is preserved for presentation as well as injection.
- Primary path: when the source composite matches the simulation grid, rendering copies the underlay into `_pixelBuffer` first, then blends simulation layers on top in configured order using each layer's own blend mode. This keeps additive and subtractive simulation behavior consistent while passthrough is on.
- In that primary path, simulation is applied as a delta from the simulation baseline onto the underlay pixel. This keeps life contrast comparable with passthrough off instead of flattening/attenuating both layers.
- The same signed additive/subtractive passthrough model now applies when the underlay stays on the shared-GPU presentation path instead of being precomposited into the CPU pixel buffer. That matters because per-layer reactive opacity can otherwise make subtractive identities behave like real subtraction and visually fade the passthrough underlay after a source-stack change flips the app onto the GPU-underlay path.
- For additive/subtractive-only stacks, passthrough uses per-family composition over the underlay with headroom normalization. Contributions are measured relative to each blend mode's identity first: additive uses raw layer color (`0` = no effect), while subtractive uses inverse distance from white (`255 - layerColor`, so white = no effect). Additive contribution is then scaled by underlay darkness (`1 - underlay`), and subtractive contribution is scaled by underlay brightness (`underlay`), which prevents one family's steady-state bias from clipping out the other when both are enabled.
- Fallback path: if the GPU composite shader/resources are unavailable for any reason, the backend falls back to CPU pre-blending of the underlay before upload so passthrough parity is preserved without depending on WPF shader effects.
- `Life Opacity` is applied to simulation contribution only; passthrough underlay intensity is not attenuated by life opacity.
- When reactive opacity drives every simulation layer to zero on a frame, the GPU path now still executes the underlay-only final composite instead of dropping back to a black simulation frame plus overlay fallback. That keeps passthrough visually stable during silence or low-level sections.
- When there are zero active simulation layers, `MainWindow` now still refreshes the source composite through the normal frame loop and then presents the CPU-readable passthrough composite directly as the final frame. That same rule applies when a `Sim Group` still exists in the scene but every child sim layer inside it is disabled. This removes the zero-layer edge case where passthrough could stay black or keep showing stale sim output simply because source/composite refresh had been tied to simulation stepping or GPU-underlay-only presentation. For inline scene-stack sim groups specifically, the final scene frame now comes from that inline resolved composite rather than from the old separate simulation-overlay presenter.
- Underlay rendering is skipped when no sources are active.

## Layer Animations

### AutoClip scheduling

- An AutoClip owns an isolated `VideoSession` instead of borrowing the path-keyed ordinary file session, so choosing a random timeline point cannot seek another layer using the same file. Probe results are requested only for selected files and then reused process-wide. Live selection enters a nonblocking preparing state until the task completes; deterministic offline rendering waits on the same bounded task. Retired decoders are disposed through one shared background media-disposal queue, and shutdown drains that queue before final process cleanup.
- Clip and delay ranges are normalized on input. Each cycle selects a random source and clip duration first, clamps that duration to the source's usable length, then selects a random media offset only from positions where the complete visible clip fits. The ordinary endpoint guard reserves up to `250 ms` (or 2% for short media) to absorb duration-probe and decoder endpoint imprecision. A non-looping zero-delay live selection separately reserves up to one second of real trailing source media, capped at 20% of source duration; this changes the eligible start window rather than forcing a rewind or enabling looping. A positive delay publishes no source frame and explicitly clears that source's `LastFrame`, so blend/key/animation processing sees the layer as absent instead of as a black rectangle or frozen clip. A nonzero fade leaves the completed outgoing phase transparent during replacement preparation.
- Each random file/offset selection requires a fresh FFmpeg command because input and seek position are fixed at process start. Zero-delay live playback uses one bounded seam, not a library-wide pool: up to one second before the scheduled boundary, the active session moves into one outgoing slot while exactly one selected successor cold-opens. The outgoing frame remains visible and continues moving while the successor is hidden. This permits at most two owned and tracked AutoClip video decoders during the seam; boundary promotion immediately requests outgoing process termination and cleanup returns ownership to one. A large process-start count over a long run therefore does not mean every library entry is being decoded concurrently. Delayed handoffs and offline rendering retain sequential, exact behavior.
- In **Loop selected file** mode, AutoClip deliberately bypasses fitted-window clamping: the selected source starts at `0`, its decoder receives `-stream_loop -1`, and the randomly chosen clip-time phase can exceed the media duration. Non-looping selections never receive `-stream_loop` merely to cover a handoff. Their zero-delay lookahead is backed only by the separately reserved real source tail and endpoint guard; if a cold open exceeds that finite tail and the outgoing decoder reaches natural EOF, capture can retain the last good outgoing frame until the successor is ready. Phase expiry still drives the same fade completion, decoder disposal, delay, and next random selection in live and fixed-duration rendering.
- Reapplying the same normalized path, clip, and delay settings leaves the current schedule intact. Fit-mode changes also keep the current decoder when fit is performed only by the compositor; exact decoder-side crop/pad/scale changes still restart with the required output command.
- Fixed-duration rendering drives AutoClip from the export frame index (`frame / output FPS`) rather than wall time. The export uses a seeded random schedule and the existing ordered offline video/audio decode path. When export ends, the pre-render live clip or remaining delay and the clip's playback position are reconstructed rather than advanced by the exported duration.
- AutoClip shares the unified output `realtime` pacing used by every live video path and never uses input `-re`. The filter preserves source/effective frame-rate metadata, applies the same three-effective-frame discontinuity limit when capped, and paces decoded successor frames even while they remain hidden. During a zero-delay seam, capture starts exactly one successor up to one second before the scheduled boundary and continues polling the visible outgoing session and its changing `FramePublishTimestamp`. The successor's publication, `VideoSession` playback clock, and optional audio stay gated until that boundary; a fresh frame arriving early does not make the new clip visible early. Hidden predecode is measured from the actual first decoded timestamp. Media age within the selected window's real trailing continuation reserve is free to the visible phase, while any excess is charged like ordinary queue age so short, non-looping sources cannot consume their whole visible window offscreen. At boundary promotion, frame ownership and the blend/key override move to the ready successor, and the outgoing process receives an immediate termination request before bounded disposal completes. Each live session still retains at most two raw frames and drops the oldest under pressure. If the UI genuinely stalls after FFmpeg has begun producing paced output, it publishes the newest retained frame and charges real post-output age against the remaining phase, preserving at least 50 ms instead of replaying a catch-up burst. If startup runs beyond the outgoing selection's actual tail and that decoder reaches natural EOF, the retained last good frame is the graceful fallback until a successor can publish. The AutoClip pause path—used when the layer or a parent group is effectively disabled, the main window is minimized, or Windows suspends—stops the phase clock, fade progression, playback/audio activation, and startup deadline while retaining the current frame. Re-enabling, restoring, or waking re-arms activation for that replacement decoder generation: a retained pre-pause frame cannot release the gate, and only a fresh frame restarts playback/audio and phase progression. The same fresh-generation hold applies when an active performance, target-resolution, or decoder-command change restarts FFmpeg. If another pause or an offline-render transition interrupts a cold open, the unpublished warm-up already spent is added to the held phase before that generation is discarded; repeated resumes therefore preserve the same fade/remaining duration. Zero delay plus zero fade keeps the outgoing clip opaque through the lookahead; a configured fade keeps that outgoing phase transparent until the new first-frame fade-in. Positive delays and offline rendering remain sequential; offline rendering uses its deterministic virtual clock and ordered frame-consumption path without live `realtime` pacing or overlap. Restoring live playback also restores elapsed/remaining clip time so a render does not restart the live fade. The requested fade is capped at half of the queue-age-adjusted visible phase.
- Normal-mode color masking/keying is source-level, so AutoClip frames use the same key color/range and GPU/CPU key-alpha calculation as file layers.
- Frame buffers and upload textures use BGRA byte layout, while UI/config key colors use standard `#RRGGBB`. D3D11 sampling exposes those textures as logical RGB, so the GPU compares sampled `.rgb` against `(KeyR, KeyG, KeyB)`; the CPU path reads BGRA bytes explicitly and makes the equivalent R/G/B comparison.
- Before either compositor draws an AutoClip frame, it resolves the session's active file path against that layer's per-video override map. Blend mode can inherit the layer or select any normal source blend; keying can inherit, force enabled with a file-specific color/range, or force disabled. CPU and GPU paths consume the same resolved blend/key structure, and changing an override does not restart the decoder or alter other files in the AutoClip.
- Color-key range uses the same nonlinear radius in the CPU and GPU compositors. The low end remains precise, while higher slider values expand enough for compressed green-screen variation without reaching distant dark colors; in particular, a bright-green key no longer partially removes black merely because the range slider is high. Pixels in the inner 82% of the selected radius are now fully transparent, with smoothing confined to the outer 18% boundary. This removes the faint tinted rectangle produced when every in-range background pixel previously retained proportional opacity.

- Each source (including layer groups) has a centered base scale (`0.10×`-`4.00×`) and can stack animations: Zoom In, Translate, Rotate, Beat Shake, Audio Granular, Fade, and DVD Bounce (with its own adjustable scale). Rotate adds its persisted start angle before its signed animated angle, so clockwise/counterclockwise changes only the animated motion. Every animation includes a cycle length in beats, so long fades can stay locked to BPM; Beat Shake uses audio beat timestamps when *Sync to Audio BPM* is enabled (falling back to the animation BPM for a timed pulse when no audio source is configured), exposes an intensity control, and ignores speed/cycle settings so its amplitude stays consistent per beat. Audio Granular now uses the fast peak-followed level signal with a soft gate, nonlinear compression, and bounded transform caps so it rides hits and releases quickly without hanging on a long average; it also applies per-animation 3-band EQ gains (Low/Mid/High) to shape zoom/translation/rotation response and supports higher intensity scaling up to 1000%. Neutral EQ (100/100/100) now maps to a stronger baseline response so the effect is clearly visible without pushing intensity to extremes.
- Video sources are decoded directly with `ffmpeg` into raw BGRA frames. The existing process-wide cached input probe records source FPS as well as the stream codec and alpha tag. Alpha-tagged VP9 selects `libvpx-vp9`, while alpha-tagged VP8 selects `libvpx`, because those decoders expose the WebM alpha plane to the BGRA pipe. Ordinary WebM and other non-alpha/native-codec inputs keep FFmpeg's default decoder selection. Normal source compositing then consumes the decoded straight alpha on both CPU and GPU paths; the resolved scene remains an opaque final presentation surface.
- Decoder-side **Fit** uses transparent-black padding for alpha-tagged VP8/VP9 rather than baking an opaque black matte around the scaled image. Fill/crop and Stretch keep their existing geometry, and ordinary opaque media keeps the standard native decode/filter path.
- Alpha-aware selection reuses the input metadata probe and the same in-memory raw-frame pipe. LifeViz does not add a second probe or create a persistent transcode/frame cache, so the fix adds no ongoing media-cache disk writes; install an FFmpeg build with the required `libvpx` decoders on `PATH` for alpha-tagged VP8/VP9 input.
- Video/YouTube layers can optionally use source audio (default off) through an in-app audio pipeline (`ffmpeg` PCM decode plus optional NAudio output). YouTube playback resolves video and audio URLs independently so audio remains available when the render path uses a video-only stream. If a source has no playable audio stream, the layer logs a warning and remains silent. Audio startup is debounced to prevent duplicate launches. Live PCM is normalized to 1024-sample, 48 kHz filter frames before `arealtime=limit=0.1` pacing rather than input `-re`, so valid long source packets are not treated as stalls while a blocked consumer still causes a bounded timestamp rebase instead of a long fast-forward burst. The pipeline is torn down when audio is toggled off, the source is removed, the app shuts down, or live media is suspended by minimization. When audio is enabled mid-playback, the decoder seeks to the current estimated video time so audio starts near the active frame instead of restarting from the beginning. Source audio gain is applied as `master volume * per-layer volume`, with a global master toggle/slider plus per-layer volume controls (including video sequences), and both are persisted/restored with source settings.
- Selecting **Audio Source > Video Stack (Silent)** switches those real-time decoders into analysis-only mode. Their stereo 48 kHz PCM is downmixed to mono into bounded two-second per-source ring buffers; each render tick drains and sums the enabled/unpaused source buffers, applies the existing master/per-layer gains, clamps the mix, and sends it directly to `AudioBeatDetector` as a real-time external input. No `WaveOutEvent` is created in this mode, so system playback from other applications is neither captured nor interrupted. The mix drives the same level, transient, beat, spectrum, seeder, reactive-mapping, and audio-synced animation paths as a device. Changing away from the video-stack selection restarts checked tracks with normal NAudio monitoring. Muted/paused/disabled layers are excluded from the mix, and bounded buffers discard oldest samples rather than adding latency if rendering falls behind.
- Video transport controls support pause/play and scrubbing. Seeking restarts decode at the requested offset (best effort) and keeps pause state; pausing stops both video decode and source audio, and resuming restarts decode from the held position. Direct-file/YouTube and sequence sessions keep their public playback clock and optional audio gated until that new generation publishes a genuinely fresh frame token, so a retained pre-pause frame cannot start catch-up. Single video/YouTube sources run in loop mode continuously, while video sequences loop at the list level.
- Base scale and animations are evaluated during compositing by transforming the destination sampling coordinates before the fit-mode mapping, so both affect injection and rendering. The transform is shared by CPU and GPU source compositors and uses the deterministic export clock during fixed-duration rendering.
- All animations share a global BPM (default 140) with per-animation half/normal/double time and forward or reverse (ping-pong) loops.

## Audio Reactivity

- Audio input is analyzed continuously (`AudioBeatDetector`) for energy and beat events.
- Device selection supports both capture inputs (microphones, via AudioGraph) and render outputs (via WASAPI loopback, including a default system output entry).
- `Input Gain` scales raw samples before energy, beat, and FFT analysis. The UI range is now tuned for real use (`0.00x..2.00x` in `0.05x` steps) instead of a huge rescue/debug range, and gain presets are tracked separately for input-device and output-device capture paths.
- Spectrum outputs are signal-gated: when RMS falls below a small floor, reported bass/frequency collapse to zero to avoid noisy "fake frequency" readings on silence. In addition to overall dominant frequency, the detector now also tracks dominant frequencies in bass, mid, and high bands for the debug overlay.
- Loudness normalization is tuned for typical program material rather than near-full-scale samples, so normal loopback playback reaches a much larger portion of the 0-1 range before clamping.
- The displayed `Audio: %` meter uses a rectified short-window max envelope signal with more normalization headroom than the slower loudness path. That keeps it responsive to hits while fitting the absolute waveform much more closely than averaged or peak-held signals.
- When **Show FPS** is enabled, `MainWindow` also draws two lightweight WPF overlay panels: a timing panel with an orange polyline from rolling frame-gap history and a red dashed frame-budget line, and an audio panel with a white waveform range trace from rolling min/max waveform buckets captured in `AudioBeatDetector`, a yellow polyline from a rolling rectified max-envelope history, a cyan polyline from rolling bass-energy history, and four note-scale frequency traces: magenta for overall dominant frequency, blue for bass-band dominant frequency, green for mid-band dominant frequency, and red for high-band dominant frequency. The text overlay also shows a recent rolling-average `Work:` breakdown for `frame_total_ms`, `build_composite_ms`, `inject_capture_ms`, `simulation_total_ms`, and `render_call_ms`, so visible-window pacing failures can be separated from actual frame-work cost. All traces use the same fixed 30-second window, with new data entering on the right and scrolling left. Yellow and cyan share the waveform zero baseline, the timing traces use a full-height `0..50 ms` scale, and the frequency traces use the full panel height on a logarithmic note-like scale. To keep WPF overlay cost bounded, the graph is resampled to a capped sample count and refreshed on split cadences: the timing panel repaints faster than the audio panel instead of forcing both to redraw together every time, and text plus the rolling gap sort refresh at 6 Hz. FFT and waveform-history scratch buffers are reused rather than allocated for every audio quantum. The audio traces come directly from `AudioBeatDetector`'s rolling history buffers, so the overlay is no longer re-sampling bass/frequency histories through additional UI-owned queues. The white trace uses bucket min/max geometry rather than one sample per bucket, which preserves waveform shape at long time scales. This stays outside the simulation render path so it does not affect GPU compositing.
- The FPS text now distinguishes `Present`, `Loop`, and `Sim`. `Present` is derived from actual render-backend draw count, `Loop` is the internal frame callback cadence, and `Sim` is simulation steps per second. That makes visible stale-present bugs diagnosable without conflating them with the scheduler cadence.
- The overlay cost itself is guarded by `pacing-current-scene-overlay-fullscreen-144`, which turns on `Show FPS` for the real saved scene in fullscreen and fails if the overlay pushes frame-gap pacing outside the same hard underrun budget used by the non-overlay pacing suites.
- Startup is guarded by a recovery flag under `%APPDATA%\\lifeviz`. If the previous session dies before `MainWindow` finishes loading, the next launch forces a safe config subset (`<=480p`, `<=60 fps`, windowed, overlay off, `Level -> Framerate` off) before initializing the saved scene so a bad persisted fullscreen/fps combination cannot brick the app on the next run.
- Legacy whole-scene `Level -> Framerate` and `Level -> Life Opacity` controls are no longer the canonical modulation path. On config load, those legacy flags are migrated into equivalent per-layer `Level -> Framerate` and `Level -> Opacity` mappings (`amount = 1 - floor`) and then cleared, so the runtime does not keep two competing systems alive. The older per-layer `AudioFrequencyHueShiftDegrees` field is also load-only now: it can still migrate old configs/projects into a `Frequency -> Hue Shift` mapping, but editor applies and later saves only persist the canonical reactive mapping list so cleared mappings do not reappear on restart.
- *Level -> Seeder* converts the same loudness signal into per-step seed burst counts (with configurable max bursts), injecting selected patterns continuously as level rises.
- When per-layer `Level -> Framerate` mappings drive a simulation layer near zero, global level seeding still injects bursts so reactivity remains visible in the frame output.
- *Beat -> Seeder* watches beat count edges and injects configurable seed bursts (Glider, R-pentomino, Random Burst) with a configurable cooldown to avoid runaway injection.
- Audio-reactive controls are gated by the selected `Audio Source`; hardware devices and the silent video-stack feed activate the same analysis paths, while `None` leaves configured reactivity inactive.
- Simulation layers can now own modular reactive mappings. Each mapping resolves one normalized input (`Level`, `Low`, `Mid`, `High`, overall `Frequency`, or band-limited frequency) into one output (`Opacity`, `Framerate`, `Hue Shift`, `Hue Speed`, `Injection Noise`, `Threshold Min`, or `Threshold Max`) plus an amount.
- Per-layer mappings are keyed to `Audio Source` selection rather than the legacy global audio-reactivity master toggle. That keeps the modular system independent from the old whole-scene controls while still falling back to a neutral state when `None` is selected.
- `Opacity` and `Framerate` mappings use multiplicative `0..1` strength against the layer's base opacity / the current global simulation target FPS. `Hue Shift` mappings add `0..360` degrees on top of the layer's base hue offset and hue-speed animation. `Hue Speed` adds up to `180 deg/s` on top of the layer's configured hue-speed animation. `Injection Noise` adds directly to the layer noise amount, `Threshold Min` raises the effective lower bound, and `Threshold Max` lowers the effective upper bound; the runtime re-normalizes the min/max pair if they cross.
- Band-energy inputs are normalized logarithmically from FFT magnitudes inside their own bins. Band-frequency inputs are log-normalized within their own frequency bands (`20..250`, `250..2000`, `2000..8000 Hz`) so the mapping behaves more like musical pitch space than linear Hz.

## Recording

- **Start Recording** captures the final output buffer, then applies a pixel-perfect integer upscale to the nearest HD height (720/1080/1440/2160 when divisible). **Recording Quality** chooses between lossless FFV1 in MKV (compressed, requires `ffmpeg`), crisp H.264 in MP4 (Windows Media Player compatible, requires `ffmpeg`), uncompressed RGB (AVI), or H.264 tiers (High/Balanced/Compact). H.264 uses quality-based VBR with bitrate caps to preserve sharp pixel edges without runaway file sizes.
- Recording uses the same final composite logic as the renderer (including passthrough precomposition/fallback behavior and invert composite), then writes frames at the configured framerate. The recording sampler tracks elapsed time against the target frame interval and fills missed intervals with duplicate frames before handing them to the async encoder queue. Normal stop pads with the last captured frame when elapsed wall-clock time is ahead of submitted frame count. This preserves constant-FPS duration/cadence while the encoder keeps up instead of collapsing skipped samples into accelerated video. Live submission is nonblocking: if the bounded queue saturates, recording fails visibly and stops rather than freezing the render thread or silently dropping queued frames. Fixed-duration rendering may wait up to five seconds for capacity because it is throughput-oriented. When **Audio Source** is a hardware device, recording starts a parallel WAV capture for that source: output devices use WASAPI loopback, input devices use the WinRT audio graph capture path. **Video Stack (Silent)** remains analysis-only and therefore produces a video-only recording. On stop, hardware-device audio is muxed into the finished video with `ffmpeg`; if audio capture or muxing fails, the video-only recording is preserved.
- The live frame-pump thread maintains the configured cadence with a high-resolution monotonic schedule and permits only one queued UI callback. That callback runs at WPF `Render` priority, alongside D3D presentation invalidation. Keeping production and presentation at the same priority prevents a continuously animated surface from starving frame production in the `Background` queue; BPM transforms and simulation steps therefore arrive evenly instead of in multi-frame bursts.
- **Render Fixed Duration...** uses the same final-frame construction, upscale, quality settings, bounded encoder queue, and output directory, but replaces the wall-clock sampler with a fixed export clock. The user selects `30`, `60`, or scene-matching output FPS (`30` by default for long-form work). Each loop iteration advances virtual time by exactly `1 / output FPS`, runs however many configured-rate simulation steps are due, renders one output frame, and submits one frame; no realtime duplicate-frame padding is used. The normal frame-pump thread is detached and every final-frame branch suppresses `PresentFrame`, GPU presentation invalidation, underlay/effect updates, and redundant presentation-layout refreshes during export. The main preview therefore remains frozen on its last displayed frame while only the progress dialog yields periodically for UI refresh and cancellation. Each refresh first uses a one-millisecond asynchronous timer, which returns through WPF's normal synchronization context even when the app is inactive. `Render`- and `Input`-priority dispatcher yields run only while the progress dialog is active: Windows can defer either queue for an inactive WPF window, so skipping them prevents focus-dependent export throttling. The progress controls keep receiving the current values and repaint/catch up on the next activation; a Cancel click activates the dialog before the next refresh, allowing those queues to drain and cancellation to finalize normally. The LifeViz process/UI thread temporarily run at above-normal priority, and offline-only ffmpeg video/audio decoders use normal priority. Original process/thread priorities are restored in finalization, and interactive decoders retain the normal low-contention policy.
- During offline export, transform animation and simulation timing read the virtual export time. GIFs also select frames from that time. File-video sessions restart without the live output `realtime` stage, apply an export-FPS filter, and use a bounded producer/consumer queue that preserves frame order instead of discarding everything except the newest decoder frame. Video sequences wait for each next decoder session before the export clock continues. The export timeline is a temporary fork: interactive decoding restarts at the exact pre-render playback offset, so the live preview does not jump forward by the rendered duration or accumulate a post-render catch-up interval.
- AutoClip tracks both the scheduler's selected successor and the file that owns the currently published frame. During a zero-delay lookahead, compositing continues to resolve blend and chroma-key overrides from the outgoing file; only boundary promotion transfers publication ownership and selects the successor's override. This prevents wrong-key flashes while the next decoder is still hidden.
- Before the encoder is created, the output filename is built inside the persisted **Recording Output Folder** (`%UserProfile%\\Videos\\LifeViz` by default). Live and fixed-duration output share this path, so removable storage can be selected once and used directly. Directory creation occurs when recording starts; an unavailable/disconnected destination is reported with its path and is never replaced by an implicit local fallback.
- Offline audio reactivity is source-backed rather than device-backed. Each enabled/unmuted video session starts a parallel unthrottled ffmpeg decoder at its current playback offset and emits 48 kHz mono float PCM. Per-frame sample counts are derived exactly from the export frame index/FPS, then active tracks are weighted by source and master volume, summed, clamped, and passed into `AudioBeatDetector` before that frame's reactive state is resolved. Beat timestamps and BPM debounce use virtual export time, so faster-than-realtime execution cannot collapse beat events. Video sequences hand analysis to the next session when their visual decoder advances. The live capture device is stopped for export and restored afterward.
- The offline audio mix is analysis-only and is not muxed into the finished file; fixed-duration output remains silent. Window/webcam sources still expose their current realtime state and can repeat samples in a faster-than-realtime export. Static images, GIFs, file videos, layer animations, and autonomous/audio-reactive simulation are the intended offline path.

## Life Modes

- **Naive Grayscale** (default): each enabled simulation layer uses a single simulation derived from a thresholded luminance mask of the capture, with per-layer Direct/Inverse input function and per-layer threshold window controls.
- **RGB Channel Bins:** each enabled simulation layer uses three independent simulations in R/G/B bins. Captures inject per-channel masks into each layer with per-layer Direct/Inverse input function; propagation stays within each channel slice (e.g., depth 24 yields bins 0-7, 8-15, 16-23).
  - Optional `RGB Hue Shift` rotates both output colors and input channel mapping (via inverse transform during mask generation), so the simulation's per-channel behavior changes with hue angle.
- **Bitwise RGB:** each enabled simulation layer uses 24 independent Conway planes. The GPU inject path quantizes the sampled RGB input to bytes, extracts all 24 bits, and injects every bit set to `1` into its corresponding plane. Planes `0-7` are red bits, `8-15` are green bits, and `16-23` are blue bits. All 24 planes evolve independently under the normal Conway step, and final color is reconstructed from the current live bit values. This mode is fixed to an effective depth of `24`, so the project depth slider does not change the plane count while bitwise mode is active.

## Binning Modes

- **Fill** (default) - channel intensity is the ratio of alive cells within the bin (frames in that channel slice). Produces smoother intensity ramps across depth.
- **Binary** - original bit-packed depth encoding; most significant bits represent newer frames, normalized to 0-255.

## Z-Stack Effect

Because every new frame pushes down the history stack, movement leaves chromatic trails. Injected window captures therefore colorize based on how recent pixels were alive, giving a time-scrubbed representation of the source window.

## Performance Notes

- Columns = round(rows * aspectRatio). The first aspect-bearing source replaces the default 16:9 ratio with its current ratio; Color Planes and plane-only groups are ignored for this choice. Removing all aspect-bearing sources restores 16:9, and the selected height (rows) stays fixed while the width adapts.
- Capture buffers are pooled (including the raw window/webcam readback), and only the downscaled composite is kept alive, removing GC spikes that caused occasional lurches.
- Disabled sources are skipped before capture and before CPU/GPU compositing. Their file, sequence, and AutoClip decoders pause, while window and webcam sessions are released; the effective state propagates through disabled parent groups. Minimizing the main window or receiving a Windows power-suspend event applies the same suspension to live media decoders; restore/wake resumes from held positions with fresh-frame activation re-armed. A fixed-duration offline export is exempt from minimization and continues while minimized. For AutoClip, suspension also freezes the active phase/fade and startup deadline, so hidden or sleeping wall time does not silently advance the random schedule.
- Window capture is paced at approximately 30 fps instead of continuously polling `PrintWindow`/BitBlt; cancellation defers GDI cleanup until an active capture exits. The GPU source compositor keeps an LRU cache of upload texture/SRV pairs keyed by source dimensions, capped at eight entries and 64 MiB, avoiding D3D11 resource churn in mixed-resolution stacks without unbounded VRAM retention.
- Normal rendering bypasses profiler stamps, per-source metric-name construction, freshness aggregation, and mapping-table rebuilds unless profiling or **Show FPS** requires them.
- Configuration changes are debounced for 500 ms and atomically persisted by one background writer. Shutdown permanently closes the FFmpeg owner first, then waits at most five seconds for the final pending config revision, so a stalled disk cannot keep media children alive. Session logs use a bounded nonblocking queue, batch/flush at most every 500 ms, and stop file output at 8 MiB per launch, keeping disk latency out of capture and UI callbacks. Expected FFmpeg `Parsed_realtime` and `Parsed_arealtime` discontinuity-reset warnings are filtered before enqueue, so an intentional stall rebase creates no additional log-write churn.
- FFmpeg process ownership is centralized for video/audio decoding, probes, recorder encoding, and muxing. Children join a Windows kill-on-close Job Object when available and are also tracked for bounded process-tree termination during ordinary shutdown; source-owned AutoClip/sequence sessions are explicitly disposed before the final manager-wide sweep. If the `PATH` entry is a Chocolatey shim, LifeViz launches the real packaged executable directly to avoid an extra shim process per operation.
- Live recording never blocks the render thread indefinitely on a saturated encoder queue. Encoder drain/finalization is bounded, while close-time teardown aborts an active recorder before the final FFmpeg sweep; normal recording stop still gets a graceful flush window.
- AutoClip uses one required decoder start per random file/seek selection. At a zero-delay live seam, the outgoing decoder and exactly one cold-opening successor may coexist; the peak is two owned/tracked AutoClip video decoders, and boundary promotion immediately requests termination of the outgoing process before cleanup returns ownership to one. The lookahead is backed by reserved real source media for non-loop clips and never changes their loop plan. Delayed and offline paths remain sequential and exact. This does not pre-open the library, retain a reusable warm decoder pool, write staged frames, transcode handoff media, or create a persistent frame/transcode cache. Frames continue through the existing bounded stdout/in-memory queues, keeping resident CPU/RAM and disk writes bounded. Increase clip durations if fewer random-input process launches are more important than frequent clip changes.
- Alpha-tagged VP8/VP9 decoder selection is metadata-only and shares the bounded probe cache above. Frames still travel through the existing stdout BGRA pipe, so transparent WebM support does not introduce a media-file writer or persistent on-disk cache.
- Random fill uses 35% seed density to encourage interesting evolution when no source is selected.
- Simulation compositing is no longer CPU-bound on the normal path. Passthrough and final presentation prefer a D3D11-backed WPF surface (`DrawingSurface`) with fullscreen shader passes for underlay blending and final simulation-layer composition, and GPU sim layers now feed that pass through shared D3D11 textures instead of CPU readback. CPU byte-buffer blending remains only as a presentation fallback or recording path; simulation layers themselves are no longer CPU-owned. CPU source readback is still required for passthrough/recording cases that need host-visible pixels. Source capture/downscale uses filtered supersampling, while the CPU compositor uses fast direct copies for already-aligned layers and bilinear remapping only when a source needs transformed or fit-mode resampling. Final display scaling remains nearest-neighbor so cell edges stay crisp. Window capture uses GDI BitBlt, so extremely large or numerous sources may require smaller grids or lower tick rates if compositing falls behind.
- WPF input interaction should stay off the render surface itself. Hover/mouse hit-testing against the GPU `DrawingSurface` can introduce avoidable UI-thread overhead, so the presentation host is treated as display-only and does not participate in focus or hit testing.
